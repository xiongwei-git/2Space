# 本地运行、数据与恢复

## 当前两种访问模式

- **新建public剪贴板**：默认凭名称查看和修改，永久保留；可设置整个空间密码。服务端保存publicKey并能读取正文，不能宣称端到端私密存储。`?readonly`只改变页面展示，去掉参数可回到编辑页；它不是隔离写权限的分享凭证。
- **既有private空间**：继续使用原v1或compact能力链接，服务端保存密文且不保存正文密钥。仅查看能力仍由服务端限制写入，读者页面不能暴露可编辑链接；不会因更新被自动转成public。旧包装密码链接继续兼容。

这一区分适用于下文所有恢复、分享和安全说明。名称公开不是密码；新模式必须避免易猜名称存放敏感内容，密码只是访问限制，不改变服务器可解密事实。

## 配置

生产：`docker compose up --build -d`。本机端口默认3210；可用 `PORT=3211 docker compose up -d` 改宿主端口，容器端口保持3210。容器非root、根文件系统只读，只有 `/data` 命名卷和临时 `/tmp` 可写。无需把运行密钥写进环境变量。`COOKIE_SECURE`在本地HTTP保持false；未来可信HTTPS部署时设置true。本轮未公网部署或修改域名。

开发：`docker compose -f compose.dev.yaml up --build`。前端5173、API3210均绑定127.0.0.1；数据和依赖使用独立开发卷。源代码挂载允许HMR；启动先装依赖，避免两个服务并发安装。修改依赖后由负责人更新lockfile并重启开发容器。

生产与开发相同端口不能同时启动；停止当前这一套再切换。不得操作其他项目的容器或卷。

## 重启持久化验收

生产容器启动后，可运行 `ACCEPTANCE_RESTART=1 node scripts/acceptance.mjs`。脚本仅创建自己的合成空间，执行 `docker compose restart app`，验证重启后密文及权限仍可用，然后清理合成空间；不删除或重建持久卷。运行前确保没有正在进行的本项目手动编辑验收。

## 数据与备份

SQLite数据库 `/data/2space.sqlite`，WAL/SHM同目录。不要仅在写入时复制主db文件；应使用SQLite备份API，或先停止本项目app容器再备份整个卷。

保守备份流程：

1. `docker compose stop app` 停止本项目写入。
2. 在本地建立私有备份目录，权限700，备份文件权限600。不要把备份放进Git仓库。
3. 用 `docker compose ps -aq app` 获取本项目容器，使用 `docker cp <container>:/data/. <private-backup-directory>` 复制整个数据目录。容器可在停止状态复制。
4. `docker compose start app`，检查health后再使用。

备份含正文密文、public空间正文key、凭证/密码哈希和元数据，仍应保密；public内容不能因文件看似密文就视为备份不可读。运营方需要自行决定备份保留周期。当前本地开发没有自动创建备份或远端上传。恢复必须先停止应用并保留现有卷副本，再将备份写到独立卷验证，不能直接覆盖唯一数据。

**旧private空间的数据库备份无法恢复丢失的客户端正文密钥或可编辑能力链接。** 这些不在服务端持久化，账号找回不属于1.0。新public空间则由服务端保留publicKey，恢复数据库可恢复内容及现有访问密码hash；不要将两种模式的恢复能力混为一谈。当前没有用户自助找回遗失空间密码的功能。

## 更新与回退

记录当前Git提交和镜像ID，备份后运行 `docker compose build`，再 `docker compose up -d`。检查 `/api/health` 与本地工作台。应用镜像回退与数据库兼容性需一起验证，不能将旧镜像当成任何迁移的通用回滚。初始1.0采用单实例SQLite，不支持多个写实例共享同一卷。

## 删除与过期

停止容器不删除数据。`docker compose down` 保留命名卷；不要执行 `docker compose down -v` 或 `docker volume rm`，除非已获得明确删除授权并核对备份。

public默认永久（retentionSeconds=0，响应expiresAt=null）；非零有30分钟至3年共12档。private旧数据原期限保持。空间过期时间由服务端执行；读取/访问统计/排序/设置密码不续期，保存正文、新增及删除页按契约续期。调整期限从上次内容保存时间起算，不修改该保存时间。到期内容不能再通过API访问，后台清理活动数据库。已有客户端副本与历史备份不随服务端删除自动消失。

## 排错

- 端口占用：先查看本项目 `docker compose ps`，选择空闲宿主端口；不要停其他项目。
- 持续unhealthy：查看本项目 `docker compose logs --tail=60 app`，确认卷可写及Node24兼容；不输出正文或能力凭证。
- 空间打不开：先判断链接是否完整、是否过期/已撤销；不要把整个能力链接提交到公开问题。
- 旧private无法解密：核对原完整链接是否还在；服务端无法重置正文密钥或替用户解密。新public打开失败应检查名称、访问密码、期限和服务响应，不能套用“服务器没有正文key”的旧解释。

## 短链接增量验收

`npm run test:links`先构建前端和后端，再用临时SQLite通过inject验证旧链接及SPA入口，不依赖/改动正在运行的3210。直接运行`node scripts/short-links-acceptance.mjs`时，必须已有前后端完整dist；干净检出应使用npm命令，不能仅构建server。此脚本和 `npm run test:visual` 都不能用现有生产数据库代替临时库。

本节对应旧private的compact增量：名称本身不授予旧private正文权限，完整可编辑/仅查看链接仍是能力凭证，禁止写入日志、截图和问题反馈。默认分享复用现有能力，显式更新/关闭才使旧读者失效。新public按上文凭名称读写，分享的是普通名称地址与仅查看页面地址，不应误用private权限承诺。任何模式都无法收回他人已复制内容。

本次契约是兼容增量迁移；部署前需由集成负责人备份当前本地数据库。不得清卷、重建旧表或强制替换旧管理密钥。旧v1链接和密码链接继续有效，空间首次绑定名称不改变正文密文或续期。恢复演练与真实生产数据迁移证据另行记录，不能由临时库回归推断。

## 整个空间密码与会话

密码由服务器scrypt加独立salt保存；非空设置/更改，留空保存移除。成功设置及解锁后发该空间的HttpOnly、SameSite=Strict、Path=/api/spaces cookie，30分钟上限；会话保存在进程内存，服务重启后需要重新输入密码。更改/移除密码会使旧会话失效，既有流也需重新验证。private还同时绑定能力tokenhash，知道密码不能绕过private凭证。

同一浏览器内同一private空间的owner/reader角色共用该空间cookie名，切换角色解锁会替换cookie，另一标签页可能重新要求密码；这是角色绑定的边界。独立浏览器上下文可独立解锁。不要通过放松token绑定解决争用。

前端3分钟无操作后显示5秒倒计时，再隐藏正文并请求lock。先在sessionStorage写入仅含spaceId的本机锁标记，成功解锁后清除；不存密码、token或正文key。若lock请求因网络失败，刷新仍先要求输入密码，避免直接用残留会话重开界面。此标记不是对同源脚本或被攻破终端的安全隔离；服务器会话仍有其独立失效规则。

### 自动锁后的未保存内容

网络失败留下的本机修改可能在自动锁后继续保留。恢复网络并输入密码只是重新打开空间，不代表已写入服务器；界面应显示“有修改尚未保存”。请检查内容，再通过“更多操作 → 立即保存”确认保存；只有服务端成功响应后才显示“已保存”。不要通过解锁流程偷偷补交来掩盖状态问题。若另一端也修改，按冲突提示选择保留副本。

对应隔离浏览器回归已检查解锁时服务器版本/内容不变、0次PUT，手动保存后恰1次PUT并解密确认正文。虚拟时钟只用于推进闲置倒计时，不代表自然等待测试；不影响正在运行的3210空间。

### 双格品牌与精简编辑器（2026-10-29）

首页、工作台与favicon采用同一双格标识，原口号为“这边复制，那边就有。”。编辑器常用入口直接显示加粗、行内代码、代码块，其他轻量富文本操作置于“更多格式”。没有表格编辑入口；图片仍属二期。

代码块各自保留语言选择、语法高亮、行号和原文复制。复制读取文档中的代码正文，包含缩进与结尾换行，不包含行号、按钮或其他界面内容。纯文本不会猜测高亮；未知入站语言按纯文本处理。Tab插入两个空格，选中多行时逐行缩进；Shift+Tab逐行去掉最多两个前导空格或一个Tab。Esc聚焦本块复制按钮，退出按钮或Ctrl/Cmd+Enter可回到普通段落。仅查看时语言禁改、退出写入动作隐藏，复制仍可用，Tab保留正常焦点导航。

常见富文本粘贴继续保留标题、强调、链接、列表、引用和行内代码。表格粘贴转成按行列顺序排列的普通文字，不保留table结构。旧文档中的表格也在浏览器显示时转换成完整文字；仅载入、选择或查看不会自动保存，服务器原revision和原密文保持。用户随后主动编辑并保存时才写入规范化文档；这不是服务端批量迁移。
